What the Demo OS is

The Demo OS is the operations system of a property preservation office, built as a showcase. It is the owner CV showcase as an operations analyst: it shows that the owner can design and run the system that keeps vacant houses safe, proved and recorded. The system in the demo has the same structure as the real one, and more views, but every property, work order, bid, invoice, payment and message in it is invented.

How it works

Every house has one record. A work order is created for a house, passes a permission gate, is carried out by a crew, is proved with before, during and after photographs, passes a photo quality check, and is submitted. Bids are written from the photographs and the record. Invoices are checked against the work before they are paid. Payments are reconciled against the invoices. Crew messages are answered in the same place, so that no instruction lives only in a phone call.

Structure of the system

  • Property Master: one record per property, with its condition, its history and its deadline.
  • Work orders: the instruction and the record for one job, travelling through eleven stops from intake to close-out.
  • Bids: written promises of scope, written in the office from photographs and records.
  • Invoices: checked against the work that was actually done and proved.
  • Payments: reconciled against the invoices, so that every payment has a matching record.
  • Crew messages: the daily conversation with crews, kept with the work it belongs to.

Six problems a new team lead must solve on day one

A new team lead arrives to a desk full of properties, orders and messages. The Demo OS is built so that six questions can be answered from one place, on the first day.

  1. Which properties are due today, and which are already late? The Property Master lists every property with its deadline, so the day starts with the list, not with a search.
  2. Which work orders are stuck, and at which stop? Every order shows its stop on the eleven-stop lifecycle, so a stuck order can be found and fixed at that stop.
  3. Which photographs prove the work, and which sets fail the Proof Test? Photo QC shows which sets pass place, time, scope and clarity, and which need to be taken again.
  4. Which bids are waiting for a decision, and what evidence do they need? The bid list shows every waiting bid with the photographs behind it.
  5. Which invoices do not match the work, and what is missing? Reconciliation compares each invoice with the work and the photographs, and flags the ones that do not agree.
  6. Which crew messages have no answer, and who is waiting on one? Crew messages sit with the work they belong to, so no instruction lives only in a phone call.

What the system does, in short:

  • Property tracking. Guards the master list of properties, one record per property.
  • Photo QC. Runs the Proof Test on every photo set.
  • Reconciliation. Flags invoice and payment lines still waiting on evidence.
  • Submission queue. Flags orders still waiting for at least one document, and the deadline each is approaching.
