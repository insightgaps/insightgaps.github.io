Advanced Edge Cases — For Experienced Preservation People

This page is why the class is not beginner-only. A beginner learns the five tools. An experienced practitioner learns where the tools break, what ambiguous orders actually look like, and what goes wrong after submission. Every example below is FAKE. Where a lesson comes from the verified training files, it says so. Where it is supplementary practice guidance, it says PRACTICE GUIDANCE — never an official rule, never an exam answer, never a client requirement. If a real order's rule sheet says something different, the order's rule sheet governs.

1. Ambiguous orders — decision rules (VERIFIED CORE + PRACTICE GUIDANCE)

Verified core: when authority, scope, or proof is uncertain, the verdict is HOLD or ESCALATE, never a guessed APPROVE. The Five Questions decide in order: SCOPE → FACTS → PROOF → PERMISSION → NEXT. A missing prerequisite is a decision, not a delay tactic.

Practice guidance — ambiguous-order decision table:

Ambiguity Default verdict What flips it
Occupancy signals conflict (one signal vacant, one signal lived-in) HOLD + escalate A verified, dated, independent occupancy proof that resolves the conflict, under the rule sheet's test
Scope says "secure" but the packet shows two different secure definitions HOLD The rule sheet section that defines secure for THIS client/programme, quoted in the verdict
Photo proves work, but not at this property HOLD Re-photographed, dated, landmark-matched proof at this property
Amount is within allowance, but no approval code is shown where the rule sheet requires one HOLD The documented approval code, or a corrected invoice within allowance
Deadline is today, proof is incomplete HOLD the incomplete line, approve only proven lines (severability) Complete proof for the held line — deadline pressure never lowers the proof standard

Experienced lesson: the most expensive verdict is not a slow HOLD. It is a fast APPROVE that adopts someone else's error — because approving a bad file adopts it, and the adoption, not the original error, is what a later audit will charge you for.

2. Photo failures — what goes wrong, in full (VERIFIED CORE)

From the verified Evidence Lab (Class 3) and the programme's photo discipline:

  • Recycled photos: same tarp, same shingles, same chimney, different house, 9 miles away in the fictional packet. Catch: Landmark-First Reverse Auditing — match landmarks before reading the claim.
  • Metadata mismatch: EXIF timestamp / season does not match the claimed date. Catch: Proof Test TIME, every photo, not just the first.
  • Crops that hide: After photo cropped to hide the uncleaned driveway, the unboarded door, the standing water. Catch: Proof Test SCOPE — does the photo show the WHOLE job claimed, or only the finished part?
  • Missing datestamp: a complete job with an incomplete proof set is not a complete submission. Catch: check the receiving system's datestamp rule FIRST — date-only for some systems, not required for others, never assume one rule fits all.
  • Neighbouring-property photos: a photo of the house next door, captioned as this house. Catch: door number, landmark, and street view in the frame, not just the caption.

Practice guidance — photo QC pass (15–30 seconds per work order, lightweight by design): (1) landmarks match this property? (2) dates/timestamps match the claimed visit? (3) Before/During/After flags correct? (4) datestamp present if the receiving system requires it? (5) nothing cropped that hides unfinished work? Fail any one → HOLD that line, state the exact failure in the Update Line.

3. Submission rejections — what goes wrong after you submit (PRACTICE GUIDANCE)

Submission is not the end of the job. It is a new audit, by a system and a reviewer who were not in the room.

  • Rejection for proof, not for work: the work was done, the proof set was incomplete, dated wrong, or flagged wrong. Lesson: submit the PROOF set, not the memory of the work. Re-check flags and datestamps before the owner cross-check, not after a rejection.
  • Rejection for bundling: a bundled line hides an over-allowable amount. Lesson: unbundle before submission, every time. A rejection for bundling costs the whole line's payment cycle, not just the excess.
  • Rejection for renumbering: the follow-up order's number does not match the original order's number, so the reviewer cannot see the chain. Lesson: in the submission note, state the chain in one line — original order, follow-up order, same property, what changed — so a stranger can follow it without asking you.
  • Rejection for a missing approval code: verbal approval, unrecorded, is not approval in the file. Lesson: if it is not in the file, it did not happen. Get the code in writing before invoicing, not after a rejection.
  • The standing discipline (verified core, not practice): complete → report the finished state → owner cross-check → submit ONLY on the owner's word, one job at a time, never on a green light alone. In the demo, there is NO submit action at all.

4. Chain / renumbered work orders (VERIFIED CORE + PRACTICE GUIDANCE)

Verified core (programme discipline): address is the matching key. Work-order numbers sometimes do NOT match across systems — the PROPERTY ADDRESS is the key. A renumbered order at the same address is the same job, not a new job plus a vanished one.

Practice guidance — chain check, every time:

  1. Match by address first, number second.
  2. List every order at that address, in date order, with its state (submitted / approved / paid / held / rejected).
  3. Ask: is this order a first order, a follow-up, or a correction of an earlier order?
  4. Ask: was payment recorded under a different number at the same address? If yes, say so in the verdict — do not call the earlier order "unpaid" on its number alone.
  5. Ask: does this order's scope overlap an earlier order's scope? If yes, severability applies: approve only the non-overlapping, proven part.

What goes wrong when the chain is skipped: double-payment for the same work, "unpaid" queues full of already-paid work, and follow-up orders approved as if they were first orders, with no record of what was already done.

5. Loss-reason discipline (VERIFIED CORE)

Verified core: every loss carries a mandatory reason code. UNEXPLAINED is a queue driven to zero, never a closed book. A loss without a reason is not a closed loss — it is an open question with a dollar amount attached.

Practice guidance — loss-reason table (use the programme's reason discipline, not invented codes):

Loss situation Reason discipline
Amount claimed above allowable, no approval code Record as over-allowable, held — not as "client deduction" until verified
Work done, proof incomplete, payment withheld Record as proof-gap, with the exact missing proof named
Payment recorded under a follow-up number Record as chain/renumbering, with both numbers and the address
Work not done, invoiced anyway Record as invalid claim, escalate — never as a routine loss
Reason genuinely unknown after checking Record as UNEXPLAINED, in the queue, with owner and date — never invent a reason to close it

Experienced lesson: a loss ledger with 60% unexplained rows does not describe a business. It describes a queue nobody worked. The discipline is not paperwork — it is the difference between knowing what you lost and guessing.

6. Datestamp and QC traps (PRACTICE GUIDANCE, from the verified photo discipline)

  • Trap 1 — datestamp on the photo, not on the caption: a caption date is not a photo datestamp. If the receiving system requires a datestamp, it must be ON the photo, in the system's required form (date-only for some systems).
  • Trap 2 — one datestamped photo does not datestamp the set: every photo in the set must pass, or the set fails. Check the set, not the first photo.
  • Trap 3 — flagging is a decision: Before / During / After flags are not filing labels. A During photo flagged as After hides unfinished work, and a reviewer who finds it will distrust the whole set.
  • Trap 4 — originals unresized: resizing, cropping, or re-compressing a photo to "make it fit" can strip metadata and break the Proof Test. Keep originals; datestamp a copy by the system's rule, never by editing the original's content.
  • Trap 5 — EXIF-only is not datestamped: if the system requires a visible datestamp, EXIF data alone does not meet it. The verified programme flags exactly this trap: photos visible as datestamped vs EXIF-only are different proof states.

7. Practitioner judgement — the questions experienced people should ask (PRACTICE GUIDANCE)

  • "What assumption is this verdict standing on, and what single fact would flip it?" — ask it of your OWN verdict, not just of a contractor's claim.
  • "Who benefits if I am wrong?" — if the answer is "the person who submitted the file", slow down.
  • "Would this verdict survive if the next reviewer had never met me, never seen this property, and only had this file?" — if not, the file is incomplete, not the reviewer.
  • "Is this a rule, or a habit?" — Beta-2 habit traps in the exam exist precisely because habits survive rule changes. Read the rule sheet on THIS order, every time.

What this page is NOT

It is not an official rulebook, not an exam key, and not a client requirement. Verified core lessons are marked as such; everything else is practice guidance for discussion and self-study. If a practice guidance line conflicts with a real order's rule sheet, the rule sheet wins — and the conflict itself is worth bringing to the trainer, because it is exactly the kind of ambiguity Class 6 exists to judge.
